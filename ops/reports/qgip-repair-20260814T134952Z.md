## Root causes, all verified directly against the 14 real acquired CSV files - not assumed

### 1. Financial-year misattribution (the "2099-00"-class defect)

The old code picked a financial-year column from the file via
`k in {"fy", "financial year", "year"}`, falling back to any column containing
`"financial year"` as a substring. For the 2012-13/2013-14 files this matched
**"Previous financial year"** - a column that, verified directly, actually holds a
**dollar amount** (values like 31818, 6000, 250, 35000...), not a year at all. When such
an amount happened to numerically resemble `20\d{2}` (e.g. an expenditure of $2037), the
code's own defensive-looking transform (`fy = f"{y}-{y+1}"`) fabricated a bogus future
financial year like "2037-38". This is the exact mechanism behind the plan's "2099-00"
observation - reproduced directly: a fresh, unmodified extraction produced facts dated
2036-37, 2042-43, 2049-50, 2057-58, ... up to 2095-96, all traced to this one column
being misread as a year.

Separately, the filename-based fallback regex `(20\d{2})\D?(\d{2})` requires a literal
4-digit "20XX" and **fails entirely** on the 5 real files using a bare two-digit "XX-YY"
pattern (`18-19-...`, `19-20-...`, `20-21-...` x2, `21-22-...`,
`...data-17-18.csv`) - every row from these 5 files (tens of thousands of real rows;
direct `wc -l` counts: 28,684 / 28,380 / 43,967 / 43,950 / 40,945 / 40,628 lines) silently
fell back to a hardcoded `"2024-25"`. Confirmed against the live database: FY2017-18
through FY2021-22 held only 2-9 facts each before this repair, while FY2016-17 and
FY2022-23 (real, correctly-attributed neighbours) held 14,209 and 18,513.

**Fix**: `financial_year` is now derived only from the filename, using a regex that
handles both two-digit and four-digit year-pair patterns
(`(?<!\d)(\d{2}|\d{4})-(\d{2})(?=[-_.]|$)`). No in-file column is ever consulted for the
year. A file whose filename yields no match is skipped entirely (visible as zero rows,
never silently defaulted to a fixed year).

### 2. Amount-column defect

The amount column was the first file-column-order match against any of
`{amount, expenditure, value, total}`. For the real 2014-15 file, **"Total funding under
this agreement"** (a whole-of-agreement, multi-year cumulative figure) precedes
**"Financial year expenditure"** (the correct single-year figure) in that file's column
order, so the wrong one was picked - reproducing the exact defect already documented for
one flagged row in `ops/reports/duplicate-fact-investigation-20260804T044328Z.md`
("QLD Murray Darling Committee Inc"), now root-caused and fixed at the source rather than
worked around per-row.

2012-13/2013-14 genuinely have **no** per-year expenditure column at all (verified: absent
from both real headers) - only the whole-of-agreement total is available for these two
years.

**Fix**: `_select_amount_col()` always prefers an actual `"financial year expenditure"`
column, regardless of file position, falling back to `"total funding under this
agreement"` only when no per-year column exists. Rows loaded from the fallback basis get
`estimate_status = "actual_cumulative_agreement_total"` instead of plain `"actual"` -
they can never be silently blended with genuine single-year figures elsewhere, per the
non-negotiable rule against summing incompatible vintages. This required a schema
migration (`021_qgip_agreement_total_estimate_status.sql`) to add the new value to the
`facts.estimate_status` CHECK constraint (SQLite requires a full table rebuild for a CHECK
change; verified byte-for-byte row-count preservation across the rebuild on a disposable
copy before ever touching the live database).

### 3. Missing subprogram structure

"Sub-program title" is present in 11 of the 14 real files (absent, genuinely, only from
2012-13/2013-14/2014-15 - verified directly, never backfilled) but was silently dropped:
the category-column heuristic picked whichever of `{"category", "description",
"supplier", "program"}` came first in file order, which is always "Program title" (it
always precedes "Sub-program title" in every file that has both).

**Fix**: `_program_and_subprogram_cols()` captures both columns explicitly. `category`
becomes `"{program} / {subprogram}"` when a non-blank subprogram exists, else just
`"{program}"` - never a trailing `" / "` or fabricated value for years/rows where it
genuinely does not exist.

## Changes

- `scripts/ingest/m7_qld_procurement.py`: `export_qgip()` rewritten per the three fixes
  above (`_fy_from_filename`, `_select_amount_col`, `_program_and_subprogram_cols`).
- `config/mappings/qld_qgip_expenditure.yaml`: added `estimate_status: estimate_status`
  (per-row column projection, already supported by the existing ETL pipeline with zero
  core code changes) and `replace_on_reload: true` (the fixed extractor changes
  `financial_year`/amount/`node_name` for most rows, producing different `fact_key`s than
  their pre-fix predecessors - without this, old defective facts would never be removed,
  just silently duplicated alongside the corrected ones; reusing the exact mechanism and
  rationale already documented in `load_facts.py` for this precise scenario).
- `scripts/ingest/migrations/021_qgip_agreement_total_estimate_status.sql` (new): adds
  `'actual_cumulative_agreement_total'` to the `estimate_status` CHECK constraint via a
  full table rebuild (SQLite has no `ALTER TABLE ... ADD CHECK`), preserving every column,
  all data, and every index exactly; the one dependent view
  (`v_fact_compatibility`) is dropped and recreated identically.
- 7 new regression tests in `tests/ingest/test_m7_qld_procurement.py` covering all three
  fixes directly (two-digit filename parsing, no-year-pattern skip, amount-column
  priority regardless of file order, cumulative-agreement-total tagging, subprogram
  capture with/without a value, absent-subprogram-column fallback).

## Remaining risks / explicitly out of scope for this repair

- **Fact-key collision / overwrite-not-sum semantics**: `load_facts.py`'s `upsert_fact()`
  uses `ON CONFLICT(fact_key) DO UPDATE SET amount_aud = excluded.amount_aud` - when
  multiple raw CSV rows (distinct real-world recipients/transactions) share an identical
  `(financial_year, node_name, measure_type, estimate_status)` identity, only the last
  one processed survives; earlier ones are silently overwritten, not summed or kept as
  separate facts. This is **pre-existing pipeline behaviour**, not introduced by this
  repair - it already applied to the old, coarser agency/program-only node identity.
  Adding subprogram as a distinguishing dimension reduces the collision rate (finer
  grouping = fewer accidental collisions) but does not eliminate it, since multiple
  distinct recipients can still share identical agency/program/subprogram text. A full
  fix would need a stable per-recipient identity (e.g. ABN) incorporated into the node/
  fact_key - a materially larger schema change than this item's three named defects,
  flagged here for a future dedicated pass rather than attempted now.
- The 2099-00-class bogus-year mechanism is now root-caused and eliminated for this
  source; the same *class* of defect (a numeric-looking column mistaken for a year) could
  recur in a different source's ad hoc column-detection heuristic and is worth a targeted
  audit of `scripts/ingest/m7_qld_procurement.py`'s twin function `analyze_disclosure_schemas`
  / the QLD contract-disclosure path, not examined in this pass.
- `dangling_source_documents` (3: `nsw_tcorp_weekly_bonds`, `qld_qtc_benchmark_bonds`,
  `qld_qtc_weekly_outstandings_2026_07_17`) is a pre-existing, unrelated finding, confirmed
  present before this repair too - out of scope here.
- Item 7.2's remaining explicit next step - a dedicated QGIP program/project explorer -
  is not attempted in this pass, per the plan's own "Then expose..." sequencing.
