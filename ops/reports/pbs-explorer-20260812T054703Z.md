# PBS explorer (Wave 4, item 6.3) and a source_key filter for /v2/tree

Generated: 2026-08-12T05:47:03Z
Repository: `ausgov-budget-tracker`, branch `main`

## Item

Plan section 6.3, sixth migration: "PBS — edition -> portfolio/entity -> outcome/program/component,
with quarantine-safe search."

## Previous behavior

16,800 `federal_pbs_programs_all` facts (post item 5.5b's reload) were loaded and live,
publishability-filtered by the item 5.5 classifier, but no frontend page existed.

The `budget_expense / accrual / <status> / <year>` compatibility triple used by PBS facts
is not exclusive to this source: other sources (state budget statements, other
PBS-derived extractors) share it. Querying `/v2/tree` with only the compatibility triple
would mix PBS rows with unrelated sources' rows in the same list - not a semantic
violation (they share a real compatibility group), but wrong for a page that claims to be
"the PBS explorer."

## Changes

- `src/backend/routers/v2/query.py`: added an optional `source_key` query parameter to
  `GET /v2/tree`, applied as an exact `source_documents.source_key` filter alongside the
  existing compatibility-triple `WHERE` clause. Omitted entirely by every caller that
  predates this parameter, preserving their existing unfiltered behaviour exactly (proven
  by a dedicated regression test, not just asserted). When present, the response `name`
  field is prefixed with the source_key so the scope is self-describing.
- `tests/api/test_v2_tree_pagination.py`: added `test_source_key_filter_narrows_a_shared_compatibility_triple`
  (proves the filtered count is strictly less than the unfiltered count for a real shared
  triple in the live database, and matches a direct SQL query joining `source_documents`)
  and `test_source_key_omitted_preserves_existing_unfiltered_behaviour`.
- `src/frontend/lib/api.ts`: extended `apiV2.tree()`'s params type with optional
  `source_key`.
- Added `src/frontend/app/explorers/pbs/page.tsx`: reuses the proven `/v2/tree` flat
  cursor-pagination pattern (same as contracts/grants/ACT invoices), scoped with
  `source_key: "federal_pbs_programs_all"` plus year and estimate_status controls
  (`budget`, `forward_estimate`, `estimated_actual`, `actual`). Page copy states rows are
  portfolio-level program/component facts, not additive to the whole-of-government tree,
  and that only classifier-publishable rows are ever shown (quarantine-safe by
  construction, since `/v2/tree` already excludes `quarantined`/`rejected` rows).
- Registered in `src/frontend/app/explorers/page.tsx`'s index.

## A debugging note (process hygiene, not a code defect)

While validating, the locally running `uvicorn` dev server kept returning unfiltered
results even after the `source_key` code change was confirmed correct in-process (via a
direct `TestClient` call) and confirmed correctly requested by the frontend (via a
Playwright network listener). Two earlier "restarts" of the dev server had not actually
replaced the running process - `ps aux` showed the same PID from the previous day still
bound to port 8000 throughout. `kill -9` on that exact PID followed by a fresh launch,
with the new PID and log output explicitly checked, resolved it immediately. No source
change was needed once the process itself was actually fresh. Recorded here because it
cost real debugging time and the fix was procedural (verify the PID actually changed)
rather than code-related.

## Data impact

None. No database write. The `source_key` addition is a new, optional, backward-compatible
query parameter on an existing endpoint.

## Dashboard impact

Once deployed, all 16,800 live `federal_pbs_programs_all` facts across every loaded
financial year and estimate status become reachable through a dedicated, correctly-scoped
explorer, truthfully paginated and never mixing in other sources that share the same
compatibility triple.

## Remaining risks

A true edition -> portfolio/entity -> outcome/program/component drill-down hierarchy
(rather than a flat list plus client-side filter) and server-side search remain part of
the larger item 6.1 explorer API, matching the scope boundary already recorded for every
other Wave 4 family. The production deployment lag (see the ledger's top-of-file callout)
continues to apply: this change, like every backend change since item 3.4, is committed
and tested on `main` but not yet live for real users.
