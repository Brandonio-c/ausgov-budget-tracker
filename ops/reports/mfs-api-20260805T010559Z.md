## `src/backend/routers/v2/mfs.py` - never part of `/v2/dashboard/*`

Wired into `src/backend/routers/v2/__init__.py` as a sibling router
(`prefix="/mfs"`), not nested under or merged into `dashboard.router`.
No `mfs_*` `compatibility_group` is registered under any
`mode_to_family` mapping (`config/compatibility/view_families.yaml`), so
this data structurally cannot reach any existing dashboard tree endpoint
even if someone tried.

### Endpoints

- `GET /v2/mfs/measures` - all 15 measure types with their semantic
  metadata (economic meaning, flow_or_stock, compatibility_group,
  accounting_basis, unit, sign convention, dashboard treatment,
  availability-window fields), sourced from
  `config/measure-semantics/mfs.yaml` plus each measure's proper label
  from `measure_definitions`.
- `GET /v2/mfs/series?measure_type=...&financial_year=...&reporting_month=...` -
  one measure's time series, filterable. Every fact response includes
  `reporting_month`, `elapsed_months` (1-11), `period_start`/`period_end`,
  and `period_granularity` explicitly - a July fact (`elapsed_months: 1`)
  can never be mistaken for a full year by a client, since the full-year
  marker (`elapsed_months: 12`/`period_end` in June) structurally never
  occurs (MFS has no June column - Task 2).
- `GET /v2/mfs/compare?measure_types=a,b,...&financial_year=...` - up to
  6 measures side by side for a comparison chart. **Never** computes an
  additive sum - always returns parallel per-measure series. Rejects
  (422, explicit message) any request mixing a `stock`/`stock_balance`
  measure with a `flow`/`balance` measure in the same call.
- `GET /v2/mfs/years?measure_type=...` - distinct financial years with
  data for a measure (drives a year selector without loading full series
  data first).

### Safeguards proven, not just asserted

| requirement | how the API enforces it |
|---|---|
| a July YTD value is never represented as a full-year value | every fact exposes `reporting_month`/`elapsed_months`/`period_end` explicitly; there is no "annual" field or label anywhere in the response, and `elapsed_months` never reaches 12 (verified: MFS has no June column) |
| a stock is never summed with a flow | `/compare` raises `422` for any stock+flow/balance mix; `/series` only ever returns one `measure_type`, so no cross-measure summation is possible there either; no endpoint anywhere computes a sum across `measure_type`s |
| incompatible measures cannot be requested as one additive series | `/compare` validates every requested `measure_type` exists and checks `flow_or_stock` compatibility before querying anything; always returns `series: [...]` (array), never a combined total field |
| annual GFS totals are unchanged | verified directly in Task 7's report against the live production API (`/v2/dashboard/tree`) before and after the load - byte-identical; reinforced structurally here since no `mfs_*` group is reachable from any dashboard endpoint |

## A documentation bug found via this endpoint, not a data bug

Testing `/years` for `mfs_stock_net_debt` returned `2007-08` as the
first year - contradicting Task 3's semantic model
(`not_published_before_financial_year: "2010-11"`). Traced to an
off-by-one bug in Task 2's own one-off manual investigation script
(clipped the true last row on 3 sheets with no trailing footnote
paragraph) - **not** the extractor or loader, both confirmed unaffected
by direct inspection of the already-loaded data. Also found the same bug
had produced a second, related error: `mfs_stock_net_worth`'s claimed
`FY2005-06` gap does not exist (present in all 26 years). Both corrected
in `config/measure-semantics/mfs.yaml` - full account in
`ops/reports/mfs-availability-window-correction-20260805T005927Z.md`. No
re-load was needed (confirmed via `--dry-run`: still 3,354/3,354 already
present, byte-identical).
